# Timbre · WebDAV 播放缓存完整方案

> 状态:**待评审**(未开始编码)
> 上游文档:`docs/plans/webdav.md`(总体方案),本文是其缓存部分的完整展开。
> 目标:在线播放**不影响流畅度**(当前章节边听边缓存、提前缓存后续章节),缓存上限可设置、可一键清除;多本书共用缓存时淘汰规则明确可预期。

---

## 1. 先回答两个核心问题

**Q1:是不是应该边听当前章节、后台缓存剩余章节?**
是。三层机制配合:

1. **写入即缓存**:播放器读到的每一块数据同时写入本地缓存(`CacheDataSource` 写穿),当前章节天然成为缓存;
2. **预取(lookahead)**:当前章节播放期间,后台按章节顺序预取**后续 N 章**(默认 5 章);
3. **优先级调度**:播放读取 > 预取写入 > 扫描分析。预取是单连接、分块、随时可暂停的任务,**播放器一进入缓冲,预取立即让路**, NAS 带宽和手机网络永远先服务播放。

**Q2:听 A 一半缓存已满,切去听 B,怎么缓存?**
**全局统一 LRU(最近最少使用)淘汰,不按书预留空间:**

- B 的数据要写入而空间不足时,淘汰"最久没被读过的缓存分片"——通常是 **A 前半本已经听完的旧章节**;
- A 的**当前章节和预取好的后续章节**因为刚被读过/刚写入,是"最近使用",暂时安全;
- A 的精确播放位置存在本地数据库,与缓存无关。回头再听 A:命中则秒开,未命中则从断点重新缓冲 1~2 秒,进度无损;
- 完整推演见第 5.3 节。

## 2. 分层架构

```
                    ExoPlayer(播放)              预取器 CacheWriter(后台)
                         │                            │
                         ▼                            ▼
              CacheDataSource(播放用)      CacheDataSource(预取用)
                         └────────────┬──────────────┘
                                      ▼
                    SimpleCache(进程内单例)  ←—— 唯一真正拥有缓存目录与索引
                    · 存储位置: context.cacheDir/webdav_cache
                    · 索引: StandaloneDatabaseProvider(sqlite,重启后重建校验)
                    · 淘汰: 自定义 LruCacheEvictor(上限可热更新,见 §6)
                                      │
                                      ▼
                            AuthDataSource(§ 注入 Basic 认证)
                                      │
                                      ▼
                     DefaultHttpDataSource(HTTP + Range)
```

- **`SimpleCache` 全进程唯一实例**:media3 要求同一目录只能有一个 `SimpleCache`,播放与预取共享它,分片级并发读写由其内部锁保证。
- **两个 `CacheDataSource` 包装同一 `SimpleCache`**:播放用(边读边写)与预取用(读完即落缓存)行为一致,只是调用方与优先级不同。
- **缓存以 span(默认约 5MB 分片)为粒度**,不是整文件:只缓存实际读过的区间。两个直接推见 §3。
- **关闭缓存(上限=关)**:不包 `CacheDataSource`,直接 `AuthDataSource` 纯流式。

## 3. 缓存粒度与键

| 项 | 设计 |
|---|---|
| 缓存键 | 章节资源 URL(即 `ChapterId`),与认证头无关——认证在下游注入,换密码不失效 |
| 粒度 | ~5MB 分片;seek 落在已缓存区间内=零网络请求 |
| **单章比整个缓存还大**(如 3GB 整本单文件 M4B) | 照常播放:只保留当前读取位置附近的分片,更早的分片按 LRU 边写边淘汰,等效于"滑动窗口缓存" |
| 命中率来源 | ① 当前章重听/回跳 ② 预取好的后续章 ③ 封面/文件头(所有分析流量也走同一缓存,重扫不再下载) |

## 4. 预取策略(lookahead)

| 项 | 设计 | 理由 |
|---|---|---|
| 触发时机 | PlaybackService 存活期间,存在"当前书"即工作 | 退出播放自动停 |
| 预取对象 | **当前活跃书**当前章节之后的章节,按播放顺序 | 多书并发预取会互相踩踏,只服务"正在听的书" |
| 预取窗口 | 设置项:**关 / 5 章(默认) / 20 章 / 整本** | 5 章×20 分钟×128kbps ≈ 95MB,覆盖一次专注收听;「整本」受上限约束,大书时实际效果=尾部 1GB,UI 提示带宽代价 |
| 并发 | **1 个连接,顺序分块读**(每块 1–4MB,块间可取消) | 对 NAS 最友好;seek 位置变化即重算窗口、取消在途预取 |
| 让路规则 | 播放器进入缓冲(复用 `PlaybackIoGate.setAwaitingPlayback`)→ 预取立即暂停,恢复后继续 | 流畅度第一 |
| 流量网络 | 默认**仅 Wi-Fi/不计费网络预取**;计费网络下只缓存播放本身读到的数据;设置项可放开 | 防止偷跑流量 |
| 失败处理 | 静默重试(指数退避,≤3 次),失败不影响播放(播放未命中时自己会走上游) | 预取只是加速,不许添乱 |
| 停止条件 | 窗口已全部缓存 / 播放停止 / 书切换 / 网络断开 | |

已播过的当前章之前的章节**不主动清理**——交给 LRU 在空间压力时自然淘汰(回头重听是真实需求,如"上一章没听清")。

## 5. 淘汰策略与多书推演

### 5.1 规则

- 全局唯一缓存池,所有服务器、所有书共享,统一 **LRU 淘汰**;
- LRU 的"使用"= 被读取或写入(media3 每次访问会刷新分片时间戳,自定义 evictor 开启 `requiresCacheSpanTouches`);
- **无需显式"保护当前章节"**:正在播放的分片每秒都在被读,永远是 MRU,数学上不会被优先淘汰;
- 淘汰触发:新分片写入导致总量 > 上限时,从最旧开始逐出,直到回落到上限以内。

### 5.2 为什么不按书预留/不保护旧书当前章节

按书预留会让"一周没动过的书 A"永久占着 500MB,而"正在听的 B"反而要反复重新缓冲——违背缓存的本意。LRU 的隐含假设(最近用过的更可能再用)对听书场景完全成立:**当前书、当前位置附近的数据,天然就是最近使用的**。

### 5.3 场景推演:A 听到 50%(缓存已满)→ 切去听 B → 再回 A

设上限 1GB,A 共 40 章(每章约 60MB),已听 1–20 章:

1. **听 A 期间**:缓存里是 A 的分片,越早听的越旧。第 20 章是 MRU,预取的 21–25 章是新写入;
2. **切到 B**:B 第 1 章开始播放+预取,需要写入 → 淘汰从"最久未用"开始 = **A 的第 1、2、3…章**(早听完的);
3. **持续听 B**:A 的旧章节陆续被逐出;A 的 20–25 章(近期使用)暂时幸存,直到 B 真正需要这 1GB 空间;
4. **回到 A**:进度从数据库恢复到第 20 章。若 20 章还在缓存 → 秒开;已被逐出 → 重新缓冲 1–2 秒后继续,预取器随即为 A 重建 21 章以后的窗口;
5. **全程无损**:A、B 的进度、书签都在数据库;缓存只是"热数据"的驻留层。

### 5.4 边界情况

| 情况 | 行为 |
|---|---|
| 单章 > 整个缓存 | span 滑动窗口,正常播放(见 §3) |
| 飞行模式 | 已缓存区间可离线播放;未缓存部分报网络错误,恢复后从断点继续 |
| 缓存写入失败(磁盘满等) | `CacheDataSource` 自动降级为直连上游,播放不受影响 |
| 上限调小 | 自定义 evictor 立即执行一轮淘汰(不等下次写入) |
| 服务器删除 / 地址变更迁移 | **按 URL 前缀清除**对应缓存条目(键即 URL,天然可过滤) |
| 进程被杀重启 | `StandaloneDatabaseProvider` 索引重建,缓存继续有效 |

## 6. 设置项与 UI(设置 → WebDAV → 播放缓存)

```
┌ 播放缓存 ────────────────────────────────┐
│  当前占用        412 MB / 1 GB      [清除缓存]
│  ──────────────────────────────────────  │
│  缓存上限        ○ 关闭  ○ 512MB ● 1GB ○ 2GB ○ 4GB
│  预取后续章节     ○ 关闭 ● 5 章 ○ 20 章 ○ 整本
│  移动网络预取     [开关] (默认关)
└──────────────────────────────────────────┘
```

- 「清除缓存」带确认对话框,显示可释放空间;清除后正在播放的章节自动走网络重缓冲;
- 「缓存上限=关闭」= 纯流式(仍可正常听,只是没有加速层);
- 上限热生效:自定义 evictor 从 DataStore 读实时值,改完立即淘汰到新上限,**无需重启播放**;从「关闭」切到某档位在下一次播放生效(避免运行中重构 `SimpleCache`)。

## 7. 与现有系统的协同

| 系统 | 交互 |
|---|---|
| 扫描/分析(远程序列) | 优先级:**播放 > 预取 > 扫描**。三者共用网络;扫描分析走同一缓存工厂,远程 M4B 头部被缓存后,重扫成本趋近于零 |
| 目录列表缓存(§4.2 主方案) | 不变,内存级 TTL 30s,与本缓存放哪无关 |
| 断网表现 | 不变:书架可浏览、播放报错、断点恢复 |
| 服务器地址迁移(主方案 §4.9) | 迁移事务里同步清除旧前缀缓存条目 |
| 本地(SAF)书 | 完全旁路,本地书数据不进此缓存 |

## 8. 落地位置与依赖

- `core/playback` 新增:`PlaybackCache`(SimpleCache 单例 + `LruCacheEvictor`)、`CachingDataSourceFactory`、`PrefetchScheduler`(协程 + CacheWriter);
- `core/webdav` 的 `AuthDataSource` 保持纯认证职责,作为 `CachingDataSourceFactory` 的上游;
- 设置持久化沿用现有 DataStore 模式;`features/settings`/`features/webdav` 增加上图 UI;
- media3 已在依赖中(`SimpleCache/CacheDataSource/CacheWriter` 都在 `media3-datasource`,随现有 `media3-exoplayer` 传递),**零新增依赖**。
