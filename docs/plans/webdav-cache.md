# Timbre · WebDAV 播放缓存完整方案

> 状态:**待评审**(未开始编码)
> 上游文档:`docs/plans/webdav.md`(总体方案),本文是其缓存部分的完整展开。
> 目标:在线播放**不影响流畅度**;**填满式预取**——听当前书时把未听章节尽量提前缓存,直到缓存上限;缓存上限可设置、可一键清除;多本书共用缓存时,淘汰规则明确、可预期,切换书籍不吃掉新书的缓存。

---

## 1. 先回答两个核心问题

**Q1:听第 1 集时,是不是应该把未听过的章节一直预缓存,直到缓存上限(如 1GB)?**
是,这是默认行为(**填满式预取**):

1. **写入即缓存**:播放器读到的每一块数据同时写入本地缓存(`CacheDataSource` 写穿);
2. **填满式预取**:当前章节播放期间,后台按章节顺序持续预取**后面所有未听章节**,直到「整本书剩余部分已全部缓存」或「缓存达到上限」二者先到为准;
3. **优先级调度**:播放读取 > 预取写入 > 扫描分析。预取是单连接、分块、随时可暂停的任务,**播放器一进入缓冲,预取立即让路**,NAS 带宽和手机网络永远先服务播放。

参考量级:128kbps 约 57MB/小时 → 1GB ≈ 17~18 小时音频,多数有声书**整本剩余部分都能装下**;超过上限的超长书自动变成"跟随播放位置前移的滑动窗口"。

**Q2:A 用未听预取把缓存填满了,这时切换到下一本书 B,怎么办?**

这是本方案的核心设计点,四个机制配合:

1. **预取只服务当前活跃书**:切到 B 的瞬间,A 的预取任务立即停止;B 一边播放,一边开始自己的填满式预取;
2. **分片分类**:每个缓存分片带标记——「**已消费**」(被播放真正读过)或「**投机**」(预取写入但从未播放过)。A 塞满缓存的主体是投机数据;
3. **分级淘汰(防预取污染)**:腾空间时,先淘汰**非活跃书的投机分片**,再按普通 LRU 淘汰其余分片。这样 B 的播放与预取能顺畅接管缓存,A 的投机预取自然消亡——否则会出现"A 没听的预取长期霸占缓存、B 反复缓冲"的预取污染;
4. **边写边淘汰,永不等待**:播放/预取的每次写入同步触发淘汰,不需要"先腾地方再播",B 从第一秒起就正常播放。

回到 A 时:进度、书签都在数据库,毫发无损;只是投机预取大概率已被清掉,当前章重新缓冲 1~2 秒,预取随即重新开始填满。**代价只是重新下载,体验无损。** 完整推演见 §5.3。

## 2. 分层架构

```
                    ExoPlayer(播放)              预取器 CacheWriter(后台)
                         │                            │
                         ▼                            ▼
              CacheDataSource(播放用)      CacheDataSource(预取用)
                         └────────────┬──────────────┘
                                      ▼
                    SimpleCache(进程内单例)  ←—— 唯一真正拥有缓存目录与索引
                    · 存储位置: context.cacheDir/webdav_cache
                    · 索引: StandaloneDatabaseProvider(sqlite,重启后重建校验)
                    · 淘汰: 自定义分级 LRU evictor(§5,上限可热更新)
                    · 分片元数据: 由 PrefetchScheduler 维护(键→分类/活跃书/时间)
                                      │
                                      ▼
                            AuthDataSource(注入 Basic 认证)
                                      │
                                      ▼
                     DefaultHttpDataSource(HTTP + Range)
```

- **`SimpleCache` 全进程唯一实例**(media3 要求同一目录仅一个),播放与预取共享,分片级并发读写由其内部锁保证;
- **两个 `CacheDataSource` 包装同一 `SimpleCache`**:播放用(边读边写)与预取用(读完落缓存);
- **缓存以 span(约 5MB 分片)为粒度**,不是整文件:只缓存实际读过的区间;
- **关闭缓存(上限=关)**:不包 `CacheDataSource`,直接 `AuthDataSource` 纯流式。

## 3. 缓存粒度与键

| 项 | 设计 |
|---|---|
| 缓存键 | 章节资源 URL(即 `ChapterId`),与认证头无关——认证在下游注入,换密码不失效 |
| 粒度 | ~5MB 分片;seek 落在已缓存区间内=零网络请求 |
| **单章比整个缓存还大**(如 3GB 整本单文件 M4B) | 照常播放:只保留当前读取位置附近的分片,更早分片按 §5 规则边写边淘汰,等效滑动窗口 |
| 命中率来源 | ① 填满式预取好的后续章节 ② 当前章重听/回跳 ③ 封面/文件头(分析流量走同一缓存,重扫几乎零下载) |

## 4. 预取策略(填满式 lookahead)

| 项 | 设计 | 理由 |
|---|---|---|
| 预取对象 | **当前活跃书**当前章节之后的所有未听章节,按播放顺序 | 多书并发预取必然互相踩踏,只服务正在听的书 |
| **停止条件** | ① 剩余章节全部缓存完毕;② **缓存达到上限**;③ 播放停止/切书/断网 | "填满即停",绝不浪费 |
| 预取模式 | 设置项:**填满整本(默认) / 固定窗口(5 或 20 章) / 关闭** | 填满是用户期望的默认;窗口模式留给想省流量的人 |
| 推进方式 | 播放位置前移 → 预取前沿自动跟随(已听章节移出预取范围,继续向后补) | 滑动窗口效果 |
| 并发 | **1 个连接,顺序分块读**(每块 1–4MB,块间可取消) | 对 NAS 最友好;seek 变化即重算窗口、取消在途预取 |
| 让路规则 | 播放器进入缓冲(复用 `PlaybackIoGate.setAwaitingPlayback`)→ 预取立即暂停,恢复后继续 | 流畅度第一 |
| 流量网络 | 默认**仅 Wi-Fi/不计费网络预取**;计费网络下只缓存播放本身读到的数据;设置项可放开 | 防止偷跑流量 |
| 失败处理 | 静默重试(指数退避,≤3 次),失败不影响播放(未命中时播放自己会走上游) | 预取只是加速,不许添乱 |
| 切书行为 | **立即取消**旧书预取任务;新书预取即刻开始 | §5 的淘汰配合,保证新书缓存不被旧书投机数据挤压 |

已听章节**不主动清理**——交给 §5 的分级 LRU 在空间压力时自然淘汰(回头重听上一章是真实需求)。

## 5. 淘汰策略:分级 LRU

### 5.1 分片分类

`PrefetchScheduler` 在本地维护轻量元数据(内存 + 随设置持久化可选):

```
cacheKey(章节 URL 分片) → { bookId, classified: CONSUMED | SPECULATIVE, lastTouchAt }
```

- **CONSUMED(已消费)**:播放器真正读过的分片(当前听的数据、回跳重听的数据);
- **SPECULATIVE(投机)**:预取写入且从未被播放读过的分片;
- 分片被播放读到的一刻,分类从 SPECULATIVE 升级为 CONSUMED,并刷新 lastTouchAt;
- **活跃书** = 当前正在播放的书(全局唯一)。

### 5.2 淘汰顺序

需要腾空间时(按分片逐个淘汰,直到回落上限内):

1. **第一优先淘汰:非活跃书的 SPECULATIVE 分片**(按 lastTouchAt 从旧到新)
   ——切书后,旧书"没听过的预取"就是这类,最先让路;
2. **第二:普通 LRU**(CONSUMED 与活跃书的 SPECULATIVE 混在一起,按 lastTouchAt 从旧到新)
   ——活跃书正在读的分片每秒都被 touch,数学上天然最安全;活跃书预取前沿最老的部分(比如很久之前预取但一直没听到的)也会在这里按时间顺序让位给更新的预取,形成自然滑动;
3. 上限调小、或点「清除缓存」时同样按此顺序执行(清除=全部)。

**为什么必须分级**:纯 LRU 下,A 切走前刚预取的几百 MB"未听数据"时间戳最新,反而最晚被淘汰;B 播放时自己的数据(同样最新)和 A 的投机数据互相挤压,结果是 B 反复缓冲、缓存命中率崩塌——这就是预取污染。分级后,"没被真正消费的投机数据"永远最先给活跃书让路,缓存始终围绕"正在听的书"组织。

### 5.3 场景推演:听 A 第 1 集填满 1GB → 切到 B → 再回 A

设上限 1GB,A 共 40 章(每章约 25MB):

1. **听 A**:第 1 章播放(边播边缓存,CONSUMED);预取器从第 2 章开始顺序预取(SPECULATIVE),直到装满 1GB——大约缓存到第 38~39 章,预取器报告"达到上限,暂停";
2. **切到 B**:A 的预取立即取消。B 第 1 章开始播放,每个分片写入时触发淘汰:**先清 A 的投机分片**(第 2~39 章里时间戳最旧的先走,几个分片就够 B 当前章用);同时 B 自己的填满式预取启动,持续用同样规则换空间。几分钟内缓存主体从 A 换成 B。A 只留下第 1 章的 CONSUMED 数据,随后也会按普通 LRU 逐渐让出;
3. **回到 A**:进度从数据库恢复(精确到第 1 章的秒数)。第 1 章可能还在缓存(秒开),也可能已被 B 挤掉(重新缓冲 1~2 秒);预取器随即为 A 重新填满 2~39 章;
4. **全程**:A、B 的进度、书签、章节表都在数据库,与缓存无关;缓存只是"热数据驻留层",任何分片都可以安全丢弃,最多付一次重新下载的代价。

### 5.4 边界情况

| 情况 | 行为 |
|---|---|
| 单章 > 整个缓存 | span 滑动窗口,正常播放(见 §3) |
| 飞行模式 | 已缓存区间可离线播放;未缓存部分报网络错误,恢复后从断点继续 |
| 缓存写入失败(磁盘满等) | `CacheDataSource` 自动降级为直连上游,播放不受影响 |
| 上限调小 | evictor 立即按 §5.2 顺序执行一轮淘汰(不等下次写入) |
| 服务器删除 / 地址变更迁移 | **按 URL 前缀清除**对应缓存条目(键即 URL,天然可过滤),对应分片元数据一并清理 |
| 进程被杀重启 | `StandaloneDatabaseProvider` 索引重建;分片分类元数据若丢失,保守起见全部视为 CONSUMED 按普通 LRU 处理(最坏情况=退化为纯 LRU,不产生错误行为) |
| 长期不活跃的书 | 其投机分片在最优先淘汰队列里自然老化,不会永久霸占 |

## 6. 设置项与 UI(设置 → WebDAV → 播放缓存)

```
┌ 播放缓存 ────────────────────────────────┐
│  当前占用        412 MB / 1 GB      [清除缓存]
│  ──────────────────────────────────────  │
│  缓存上限        ○ 关闭  ○ 512MB ● 1GB ○ 2GB ○ 4GB
│  预取            ● 填满整本 ○ 20 章 ○ 5 章 ○ 关闭
│  移动网络预取     [开关] (默认关)
└──────────────────────────────────────────┘
```

- 「清除缓存」带确认对话框,显示可释放空间;清除后正在播放的章节自动走网络重缓冲;
- 「缓存上限=关闭」= 纯流式(仍可正常听,没有加速层,预取选项同时隐藏);
- 上限与预取模式热生效:改完立即生效(可能立即触发一轮淘汰),**无需重启播放**;从「关闭」切到某档位在下一次播放生效(避免运行中重构 `SimpleCache`);
- 占用量从 `SimpleCache` 索引实时读取。

## 7. 与现有系统的协同

| 系统 | 交互 |
|---|---|
| 扫描/分析(远程序列) | 优先级:**播放 > 预取 > 扫描**。三者共用网络与缓存工厂;远程 M4B 头部被缓存后,重扫成本趋近于零 |
| 目录列表缓存(主方案 §4.2) | 不变,内存级 TTL 30s,与本缓存无关 |
| 断网表现 | 不变:书架可浏览、播放报错、断点恢复 |
| 服务器地址迁移(主方案 §4.9) | 迁移事务里同步清除旧前缀缓存条目与分类元数据 |
| 本地(SAF)书 | 完全旁路,本地书数据不进此缓存 |

## 8. 落地位置与依赖

- `core/playback` 新增:`PlaybackCache`(SimpleCache 单例)、`TieredLruCacheEvictor`(§5.2 分级淘汰,实现 media3 `CacheEvictor`)、`CachingDataSourceFactory`、`PrefetchScheduler`(协程 + media3 `CacheWriter`,负责预取推进与分片分类元数据);
- `core/webdav` 的 `AuthDataSource` 保持纯认证职责,作为 `CachingDataSourceFactory` 的上游;
- 设置持久化沿用现有 DataStore 模式;`features/settings`/`features/webdav` 增加上图 UI;
- media3 已在依赖中(`SimpleCache/CacheDataSource/CacheWriter/CacheEvictor` 都随现有 `media3-exoplayer`/`media3-datasource` 传递),**零新增依赖**。

## 9. 测试计划

- **evictor 单测**:分级顺序(非活跃投机最先)、touch 刷新分类升级、上限热更新立即淘汰、0 上限旁路、元数据丢失退化为纯 LRU;
- **预取调度单测**(fake 时钟 + MockWebServer):填满即停、上限触达暂停、播放推进跟随、切书取消与让路、计费网络门控、失败重试上限;
- **集成**:临时目录真实 `SimpleCache` 验证 命中/未命中/部分命中(单章大于缓存)、并发播放+预取锁、清除与按前缀清除;
- **多书推演回归**:按 §5.3 脚本断言淘汰顺序与 B 的命中率。
